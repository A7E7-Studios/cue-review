# Architecture

CueReview is a desktop application for recording a review, replaying its video alongside a local transcript, and handing selected evidence to an agent. Windows is the hardware-verified platform; macOS and Linux builds share the same code with platform capture backends. Tauri owns native operations; React owns presentation and playback. Recording data stays in local project/session folders. No account or hosted inference service is required.

## Responsibilities

| Component | Responsibility |
| --- | --- |
| React/WebView2 | Session navigation and search, source selection, playback, word seeking, transcript, takes, settings, window chrome |
| Tauri/Rust | Validate command arguments, own capture processes and devices, persist metadata, run local media/transcription jobs |
| Windows Graphics Capture | Capture a selected display or window through `windows-capture` |
| Cursor sampler (`cursor.rs`) | Record the pointer and its buttons beside Windows display/window captures |
| CPAL/WASAPI | Capture the selected microphone and optional system output loopback |
| scrcpy/ADB | Capture authorized Android devices, including compatible Quest devices |
| FFmpeg/ffprobe | Normalize and combine media, append takes, inspect duration, extract frames and clips |
| whisper.cpp | Transcribe local audio and produce timestamped token JSON |
| Agent CLI (`cli.rs`, `agent.rs`, `bin/cue.rs`) | Discover sessions and retrieve transcript, frame, clip, cursor and moment evidence |

The implementation uses one active recording at a time. Long operations must run outside the UI thread. Native errors must reach the interface with recovery details; dependency or hardware failures must never return demonstration data.

The window chrome is part of the web UI on Windows: the window has no native decorations, and `src/chrome/TitleBar.tsx` draws the title bar with the Minimize, Maximize/Restore and Close controls through `src/chrome/windowApi.ts`. macOS uses an overlay title bar with the native traffic lights; Linux keeps native decorations. The backend still refuses to close while recording or processing, whichever control asks. See [DESIGN.md](DESIGN.md).

## Capture and synchronization

Windows Graphics Capture is the native display/window path. FFmpeg `gdigrab` is not a substitute for universally supported system audio: DirectShow only exposes configured capture devices. WASAPI loopback reads the rendering endpoint without requiring Stereo Mix or a virtual audio driver.

Microphone and system audio have independent clocks. Retain capture offsets against one session origin, preserve silence and discontinuities, and align streams when producing the playback file. A recording must remain in sync when the output device is silent for several seconds. Muting a microphone must write silence without collapsing the timeline.

`AudioWriter` (`capture.rs`) writes each track (`mic.wav`, `system.wav`) back to back as the device delivers it, as mono 32-bit float; placing a packet by its timestamp × the nominal rate would leave a short hole wherever the device runs slow, heard as crackle. The WASAPI capture timestamps split the packets into runs at every pause of more than 50 ms (a glitch, or loopback while nothing plays), give each run its start in the take, and measure the device's clock against the wall clock over the runs' own audio. At Stop, `finish` rewrites the track: each run resampled by that ratio with a 32-tap Blackman-windowed sinc (a 1024-phase table, streamed from the file) and placed at its start by the wall clock, silence before, between and after the runs, so the track is exactly the take's length and a gap cannot shift what follows. A ratio more than 5% from 1, or under a second of audio, is not trusted and counts as 1. While recording, gaps are written as wall-clock silence so live snapshots read the track roughly in place, before that correction.

Windows Graphics Capture may emit frames only when the image changes. Stopping must be independent of receiving another frame. Encoder finalization is required after normal stop, source closure, and capture errors. A final static interval must remain represented in the finished video's duration.

scrcpy records encoded device streams with device timestamps. Those timestamps preserve device audio/video alignment; they do not automatically synchronize a separately captured PC microphone. The implementation must account for device startup latency and document any remaining alignment limit. When the display turns between portrait and landscape, scrcpy restarts its encoder at the other size, and FFmpeg rebuilds a filter graph at a size change, restarting `setpts=PTS-STARTPTS` and `tpad`, which lost or misplaced every frame after it. So when a key-frame probe (`-skip_frame nokey`) finds more than one frame size, `finalize` first letterboxes every frame onto the first frame's size with stateless filters (`scale`, `pad`) and their timestamps passed through, then muxes that as usual; `capture-timing.json` records `frameSizes`. ADB authorization and a connected device are required. Quest compatibility must be checked on the actual headset rather than inferred from Android support.

Previews use a continuous MJPEG response over an ephemeral loopback listener with a random per-stream URL token. There is no screenshot polling or per-frame React state update. Windows capture pushes JPEG frames directly; device previews run the installed matching scrcpy server in video-only raw-stream mode on a unique ADB forward and decode H.264 with FFmpeg. Cameras use a continuous DirectShow/FFmpeg capture. Only the latest frame is retained if the viewer falls behind. Preview resolution is bounded independently of recording resolution. Starting a recording keeps the existing preview stream; switching sources or entering review stops its owned resources. Frontend start/stop operations are ordered, and stale stop IDs cannot terminate a newer stream. Source errors reach the UI through a Tauri channel. Meta/Oculus Quest virtual-camera filters are excluded from enumeration in favor of authorized USB devices.

Final playback encoding uses x264 veryfast CRF23, retaining capture resolution and frame rate. A successful encoder exit is followed by stream and duration validation; only a clean capture with verified output removes its owned native-video.mp4 or native-video.mkv intermediate. Capture/finalization failures retain the native video. Lossless audio and transcription evidence remain available for retry. A Windows capture without microphone or system audio still gets a silent audio track, because appending a take needs an audio track on both sides. This policy applies to new captures, without retroactive changes to existing recordings.

## Takes (Record more)

"Record more" continues a ready session as a new take (`src-tauri/src/takes.rs`, plan decision 10).

**Layout.** Take 1 is the session folder itself, so every recording made before takes existed is a one-take session and needs no migration. Take N records into `sessions/<id>/takes/<N>/` with the same files a single recording has. `video.mp4` in the session folder is the combined recording. `session.json` lists the takes once there is a second one: `takes: [{index, offsetMs, durationMs, status, folder, microphoneId?, systemAudio}]`. A legacy session's take 1 is synthesized from the session until Record more writes it out. Folders are always derived from the take index, never from `folder` or other metadata, so a damaged `session.json` cannot redirect cleanup.

**Offsets.** Starting a take probes the combined `video.mp4`; that validated duration becomes the take's `offsetMs`. The source is locked to the session's source; microphone and system audio can be chosen again for each take. While recording, `get_recording_status` reports `takeIndex` and `takeOffsetMs`; `elapsedMs` stays relative to the take. Live transcription shifts its words by the offset, so live words land on the combined timeline.

**Source identity.** A `window:HWND` or `monitor:N` id can name something else after a restart, so the first capture (the app's Record and `cue record`) stores `sourceIdentity` in `session.json`: `{kind:"window", title, process, class, pid, processCreatedMs}` (the process image name, the window class, and the owning process id and its creation time in ms since the Unix epoch from `GetProcessTimes`) or `{kind:"display", device, left, top, right, bottom}` (the GDI device name and the monitor bounds in physical pixels). Record more re-enumerates the source and continues only when the id still resolves to the same source: a window of the same process image and window class, owned by the same process (the same `pid` and `processCreatedMs`), or the same display device. A window cannot outlive its process, so a window that is still open always passes; after a restart, a handle that now names another window of the same app (ApplicationFrameHost, Explorer, a browser) belongs to another process, or to a process that reused the id later, and is refused. When the process cannot be opened, `processCreatedMs` is left out and the process id alone must match; windows stored before these fields existed compare image and class only. Titles and display bounds may change between takes; a browser that switched tabs is still the same window, and a resolution change is normalized like any other size change. Otherwise Record more fails before anything changes with "The original window/display for this recording is no longer available. Start a new recording to capture another source." The app shows this, like any Record more refusal, under the recording bar with a New recording action. Sessions recorded before identities existed may continue a display that is still attached, but never a window. Device and camera sources have no identity and are not checked; macOS and Linux store none.

**Lifecycle.** A take's status runs `recording` → `finalizing` → `swapping` → `transcribing` → `ready` or `error`. A take is on the combined timeline exactly when it is `transcribing`, `ready` or `error`, so `error` always means "on the timeline, transcript missing". A take whose capture produced no usable video, or that the app lost while recording, becomes `interrupted`: it is not on the timeline and its folder keeps whatever was captured. Stop first probes the take's own `video.mp4`, then appends it, then transcribes it, re-reading `session.json` under the session lock at each step. Stop returns before the swap finishes; the session stays `processing` until it does.

**Discarding a take.** A take whose swap keeps failing (a `video.mp4` that matches neither duration, a take that cannot be normalized or verified, a damaged `capture-timing.json`) would otherwise block Record more and `cue transcribe` for good. `discard_take(id, index)` and `cue discard-take ID INDEX` drop a `swapping` take 2 or later: it becomes `interrupted` and keeps its folder, a waiting `swap.json` and its temporary file, `normalized.mp4` and the ffconcat list are removed, the session settles (to `ready` unless another take needs work) and `transcript.takes` is recomputed. A take on the timeline, take 1 and a session that is recording or processing are refused, and so is a `swapping` take that `video.mp4` already contains (its duration says the swap was applied, then something failed before the bookkeeping): "Take N is already in video.mp4, so it cannot be discarded. Choose Retry to finish adding it." Retry then only records the new duration and transcribes the take. In the app, a session in `error` with a `swapping` take offers "Discard take N" beside Retry transcription; after a confirmation it rereads the transcript and loads `video.mp4` again under a new cache-buster.

**Swap.** Appending writes `video.<uuid>.tmp.mp4` with the FFmpeg concat demuxer: an ffconcat list with each file's exact duration, the video stream-copied and `-copyts` so the AAC priming packet does not shift the timeline. The audio track is built once from every take's lossless `audio.wav` (take 1's in the session folder), each trimmed or padded to exactly its place on the timeline and concatenated, then encoded to AAC, so no take's audio goes through AAC more than once however many takes follow. When an earlier take has no `audio.wav`, the listed videos' AAC audio is re-encoded instead, as before. A take with another frame size, rate or pixel format is first re-encoded to the combined video's format (`normalized.mp4`): scaled uniformly to fit, centered with even padding, and the placement is recorded as `normalize{scale, padX, padY, baseWidth, baseHeight}` in the take's `capture-timing.json`. A stream copy keeps only the first file's codec setup, so when the normalized take's profile or extradata (SPS/PPS) still differs, for example after a legacy take 1 from another x264 build, the whole video is re-encoded with x264 veryfast CRF 23 instead. The temporary file must last the previous duration plus the take (within a third of the take, at most 150 ms) and decode cleanly with video and audio on both sides of the boundary. Only then does it replace `video.mp4`. `normalized.mp4` and the ffconcat list are removed once the temporary file is written or the attempt fails. Windows refuses to replace a file that a player holds open, so the rename is retried with backoff (100 ms to 3 s, about 6 s in total). If it is still refused, `takes/<N>/swap.json` names the validated temporary file and the take stays `swapping`; Retry, or the next start, finishes it without rebuilding. The UI unloads the video before Record more and reloads it with a cache-buster afterwards. After a verified swap the take's own video copies are removed: `video.mp4`, `native-video.*` and the live transcription scratch in `live/`. Its lossless audio stays for transcription retries and later audio rebuilds, with its timing and cursor track. During the swap the session briefly needs about twice the size of `video.mp4`.

**Transcription.** Only the new take is transcribed, from its own audio, and its segments are shifted by its offset and given `t{N}-` id prefixes before they replace that take's segments in `transcript.json`. `transcript.takes` lists one `{index, startMs}` mark per take on the timeline (none for a single take); the UI draws "Take N · m:ss" dividers and scrubber ticks from it, and `cue transcript --segments` prints `── Take N · m:ss ──` lines. The marks are saved even when the take's transcription fails (for example, the model is missing), so its divider and tick appear before its words. Retry works on the unfinished takes (`swapping`, `transcribing`, `error`), or every take on the timeline when none is unfinished. Record more is refused while any take is unfinished, and Copy for agent is disabled while recording. `cue transcribe` refuses while a take is `swapping` and names `cue discard-take` as the way out.

**Recovery at startup.** `Store::recover_interrupted` repairs every session the app did not finish:

| State found | Single-take session | Take N of a multi-take session |
| --- | --- | --- |
| `recording`, `finalizing` | Session `error`, original media retained, Retry offered when video exists | Take `interrupted`, raw tracks kept in `takes/<N>/`, earlier takes intact. A `finalizing` take whose own `video.mp4` was finished and probes as valid becomes `swapping` instead, so Retry adds it |
| `swapping` | — | `video.mp4`'s duration decides: already appended → take `error` (transcript missing); a validated `swap.json` file waiting → moved into place, then `error`; otherwise the take stays `swapping` for Retry |
| `transcribing` / `processing` | Session `error`, retained media, Retry | Take `error`, so Retry transcribes only that take |
| Stray `video.*.tmp.mp4`, `concat-t*.ffconcat` | — | Deleted, except a temporary file a `swap.json` still names |

A session then settles: `error` with a message naming the first unfinished take, or `ready`. A session whose `session.json` cannot be read or repaired is skipped and logged, so one damaged recording never keeps the app from starting. A skipped session that was still `recording` or `processing` is marked `error` with a message the app shows ("The app closed before this recording finished, and CueReview could not repair it when it started again: …"), so it offers Retry and Delete instead of looking busy forever. Listing sessions (the sidebar, `cue sessions`) likewise skips and logs a `session.json` that cannot be read, so a torn file never hides the rest of the library.

## Cursor tracking

On Windows, display and window recordings run a sampler thread beside the capture (`src-tauri/src/cursor.rs`), for the app and `cue record` alike. It starts once the first video frame has arrived and is stopped and joined first when the capture stops, so every sample lies inside the take. About 60 times a second it reads `GetCursorPos` and the left, right and middle buttons through `GetAsyncKeyState`, honoring swapped buttons; a press and release between two polls is still written. The thread is per-monitor-v2 DPI aware, so coordinates are physical pixels, like the captured frames.

**Clock.** Samples are timed on the capture epoch, which is also t=0 of the take's video, audio and transcript words. Adding the take's offset puts them on the session timeline.

**Origin.** Positions are relative to the top-left corner of the source, which is the top-left corner of the canvas (the first frame's size). For a display it is the monitor bounds from `GetMonitorInfoW`; for a window, the DWM extended frame bounds, re-read on every sample because the window can move. `WindowFromPoint` records whether the pointer was over the source window or something covering it. A pointer on another monitor is outside the source; a minimized or closed window, or the secure desktop (UAC, lock screen), is a gap.

**File.** Each take writes `cursor.jsonl` in its take folder: a header line (`{"format":"cuereview-cursor","version":1,"source":"window","canvasWidth":…,"canvasHeight":…,"sampleHz":60}`), then delta-encoded integer arrays: `[dt, dx, dy]` for a move, `[dt, dx, dy, state]` when the button/outside state changes, `[dt]` for a gap. A line is written on every change and at least every 250 ms. The file is append-only and flushed about once a second, so a crash loses at most the last second; readers stop at the first unparsable line. `capture-timing.json` records the canvas size and `cursorLines` or `cursorError`.

**Touch on Android.** `android:<serial>` recordings write touches into the same file, on every platform (`src-tauri/src/touch.rs`). scrcpy runs with `--no-control`, so the host pointer never reaches the device; instead a reader thread starts with the capture, beside scrcpy, and is stopped and joined first, like the sampler. It starts `adb shell getevent -lt` (no root) on every input device at once, then one `adb shell` probe reads the product model, `getevent -lp` and the display rotation. A pump thread stamps each line as it is read and queues it until the touchscreens and the canvas are known (the canvas once scrcpy has decoded its first frame), so a tap made right after Record, even before the first frame, is kept. The track is flushed about once a second. The stop kills the `getevent` client, which also ends `getevent` on the device, and any probe still running, so it never waits for one. A `getevent` that cannot open a touchscreen (stderr) or ends before the take does (the device went away) gives the take a `cursorError`; what it wrote stays. Meta Quest is skipped: its controllers and hand tracking are not Android input devices. Touchscreens are the devices with `ABS_MT_POSITION_X`/`Y` and `ABS_MT_SLOT` (multitouch protocol B), except touchpads (`INPUT_PROP_POINTER`), narrowed to the `INPUT_PROP_DIRECT` ones when any has it; the emulator's panels have no properties and come one per display, so several are read and the first to touch owns the track until it lifts. A contact whose tool type is `MT_TOOL_PALM` does not touch, as InputReader cancels palm pointers; one that turns into a finger touches down then. The Pixel 8 flags some deliberate taps near its corners as palms throughout, and Android ignores those too. Only the primary contact is written: the finger that touched down while no other finger was down. Fingers added to it, and the rest of the gesture once it lifts, are ignored. That keeps the file at version 1, so `cue` 0.2.0 reads device takes too. A touch-down is a sample with no buttons and a `LEFT` sample at the same place and time, so every touch is a press; moves are `LEFT` samples; a lift, or `SYN_DROPPED`, is a release at the last place and a gap, since touch has no hover position. A resting finger gets heartbeats. The header's `source` is `"device"`.

**Touch mapping.** A raw position becomes the pixel center of its raw step as a fraction of the axis range (`max - min + 1` steps, as InputReader scales a panel onto its display), then is rotated by display 0's rotation, as InputReader applies it: `orientation=` on the display-0 viewport line of `dumpsys input` (Android 9+), else `SurfaceOrientation:` (older). The rotation is read at the start, then again at a touch-down at least a second after the last read. The rotated fraction of the canvas is the canvas pixel. The canvas is the first decoded scrcpy texture (`INFO: Texture: WxH`, the recorded frame size, now also written to `capture-timing.json` for device takes). scrcpy scales the whole display into a video rounded to multiples of 8, so fractions carry over. A rotation that keeps the canvas's shape maps exactly. After a portrait/landscape rotation the frames have the canvas's size turned on its side, and `finalize` letterboxes them onto the canvas (see device capture above), so the rotated fraction is placed in that letterbox instead: `capture::letterbox` computes it for both. Whether the current shape differs comes from the rotation against the one read at the start.

**Touch clock.** `getevent -t` stamps each event with the device clock. The reader adds the smallest receive-minus-stamp difference among the frames of the last 20–30 s (three 10 s periods of host time; the frame that crossed adb fastest), so samples keep the device's own spacing whatever adb buffering does. The window follows a device clock that drifts against the host's either way: a minimum kept for the whole take would follow only one that runs fast, and one 50 ppm slow would put times 90 ms early after 30 minutes. `capture-timing.json` records `touchDelayMs` (`frames`, `p50`, `p95`, `max`): how much later than that fastest frame the others reached the reader. Lines are stamped by the pump as they are read, so the reader's rotation reads delay nothing. The video runs behind the device by scrcpy's capture, encode, transfer and decode time, because its first decoded frame anchors the video at `videoHostStartMs`. A frame exported at a touch's `tMs` therefore shows the screen just before the finger landed. Android's "Show taps" dot appeared in the 30 fps video a median 99 ms (77–128 ms) after the touch's `tMs` on a Pixel 8, and 89–128 ms on the Android 15 emulator (that includes drawing the dot); `touchDelayMs` was 4.0 and 0.4 ms at the median.

**Queries.** `cursor::load` stitches every take's track onto the session timeline with its offset and ends each take with a gap. It reads each take from the folder its index names, never from `Take.folder`. `at(t)` returns the nearest earlier sample unless it is a gap or older than 750 ms; `clicks` lists presses. `x`/`y` are fractions of the canvas measured at the pixel center; `px`/`py` scale them to the session video, which is take 1's canvas rounded down to even sizes; `inVideo` is false outside the canvas or when the pointer was not over the source. The CLI attaches `cursor` to transcript words and segments (`--json`), `find`, `frame`, `frames` and `moments`, and `--mark-cursor` draws a ring on exported PNGs. JSON output only gains fields, so older consumers keep working.

**Limits.** Polling can miss clicks shorter than about 16 ms. `px`/`py` for a later take recorded at a different canvas size are mapped through that take's `normalize` scale and padding, and `in_video` is false inside the padding. FFmpeg rounds the scaled size to even pixels, so the non-limiting axis can be off by less than a pixel. Touch: evdev sends only changed values and `getevent -lp` reports 0 for multitouch axes, so a slot's position is unknown until both axes have been reported once in the take, and a first touch that lands exactly on the slot's previous raw x or y is not written. `SYN_DROPPED` releases the press, starts a gap and forgets every contact, so a finger already down is not followed until it touches again. Only touches before `getevent` itself is running (an adb round trip after Record) are missed. A touch within a second of a rotation can use the previous rotation. The panel's natural orientation is assumed to match the display's, which an IDC `touch.orientation` would break. Extra fingers are not recorded. Quest, macOS and Linux desktops, and cameras have no track, and `load` returns nothing. The module notes in `cursor.rs` describe what macOS (`CGEventGetLocation` and display bounds) and Linux X11 (`XQueryPointer`) would need; Wayland exposes no global pointer position outside the screencast portal.

## Local transcription

Convert the transcription input to mono, 16 kHz signed 16-bit PCM WAV. Run the local `whisper-cli` with a locally stored model and full JSON output. A multilingual model supports automatic language selection; an English-only model should only be selected for English recordings.

Before inference, the bundled `whisper-vad-speech-segments` executable checks the entire input with a pinned Silero v6.2.0 model. A valid zero-region result produces an empty transcript. Any detected speech passes the original, unchanged PCM to Whisper, preserving its playback clock. Detector errors or malformed output remain failures with diagnostics, never silent success. This whole-input gate suppresses the tested noise-only hallucinations; it does not remove noise from mixed speech/noise recordings. The detector can also miss speech.

Whisper token timestamps are estimates. Retain the original JSON. Construct display words by joining continuation tokens and punctuation, excluding model control tokens. Never manufacture word timings by evenly dividing a sentence. Store all UI/CLI offsets in milliseconds from the playback origin; seek only within the available media duration. Silence between words must clear the active-word highlight.

Leading silence can substantially distort the first word's estimated interval: a ten-second delayed fixture placed its first word near zero while later words retained their original clock. The standard model therefore enables DTW with flash attention disabled. Its token alignment points populate optional word `seekMs` fields, preserving raw `startMs`/`endMs`. Word and sentence clicks and phrase-based frame extraction prefer these points. Highlighting uses a short visual pulse near an alignment point, not a fabricated spoken interval; old transcripts retain interval highlighting. Live updates shift alignment points onto the session clock and bound them to the snapshot. Custom models require an explicit compatible `CUEREVIEW_DTW_MODEL` preset to enable this path.

Alignment increased the measured two-thread inference time from roughly 2.2 to 4.0 seconds. It supplies estimated points, not corrected spoken durations. Direct Whisper VAD transcription altered the tested token clock, so the detector remains a whole-input gate and recognition receives the original PCM unchanged.

Transcription failure must preserve playable recorded media and offer retry. An empty result from silent audio is a valid empty transcript, not a fabricated paragraph.

During recording, a background worker takes an audio snapshot after about eight seconds and repeats after each inference plus another eight seconds. Each snapshot contains at most the latest 30 seconds. Whisper works in the session's `live` scratch directory, outside the capture/state lock. Snapshot-relative words receive the session offset (plus the take's offset for a later take); the overlapping provisional tail is replaced while earlier words remain. Results publish only for the still-active session. Stopping cancels the live subprocess, and a shared inference lock prevents overlap with final full-recording transcription. Updates arrive after local inference completes; their wording and timing can change until the final pass.

Live snapshots use the PC microphone, or Windows loopback when no microphone is selected. Android device audio by itself has no local PCM snapshot track and is transcribed after stopping; selecting a PC microphone enables progressive commentary for device reviews.

## Settings and decoding policy

App-wide preferences live in `<root>/settings.json` (`src-tauri/src/settings.rs`), shared by the app (`get_settings`/`save_settings`) and the CLI. Saving validates, normalizes and writes the file atomically; a missing or unreadable file falls back to the defaults, so it never blocks recording or transcription. Every field is optional, so older and newer files stay readable.

`settings::decoding_args` builds the Whisper options for every final and live transcription: `-l auto -ojf -ng`, then `-nf -nth 0.3` so noise is not retried at higher temperatures. Without a vocabulary it passes `-mc 0`, which carries no decoded text into later 30-second windows and avoids repeating a hallucination across them.

The vocabulary is off by default. It accepts at most 20 terms separated by commas or new lines, 200 characters joined with ", ", and an estimated 75 prompt tokens, in printable ASCII only (on Windows, `whisper-cli` reads its arguments in the ANSI code page). The Settings dialog applies the same rules before saving, and the backend validates again. When it is set, the args become `-mc <prompt tokens + 1> --prompt "<terms>" --carry-initial-prompt`: the prompt is repeated in every window, and the context budget leaves no room for decoded text, which keeps the `-mc 0` behavior otherwise. The exact token count comes from the model's own tokenizer, by a short `whisper-cli` probe that stops before the encoder runs, cached per process. A failed probe is cached too, and a probe still running after 20 s is killed, because it can run while the inference lock is held; only a missing model is not cached, so installing it takes effect at once. A prompt whose real count exceeds 96 tokens, or whose count cannot be measured (for example, no model yet), is not used, and decoding stays as without it. Measurements behind these limits are in the module notes: even 23 carried tokens let a hallucination repeat across a noisy recording, and prompts of 130 tokens or more invented lists on noise.

## Agent CLI

`cue` is a thin binary (`src-tauri/src/bin/cue.rs`) over the library:

- `cli.rs` is pure: the argument parser, per-command help and the plain-text formatters (`--segments`, clocks). `cargo test --lib` covers it. `cue.rs` is one call to `cli::dispatch`, which parses first; `--help`, `-h` and `help COMMAND` print and exit 0 before the store is opened or a lock is taken, and an unknown option or a missing value is an error that points at the command's help. It then opens the store, takes the process lock when the command needs it and runs the command while holding it.
- `agent.rs` holds the handoff text (Copy for agent), phrase search, frame and batch-frame export, clips and moments. Frames are scaled down with `--max-width` and never up, written to new files only, and an invalid batch writes nothing; when one frame of a batch fails, the frames it already wrote are deleted. `--output` and `--output-dir` must be local paths: URLs and FFmpeg protocols (`pipe:1`, `tcp://…`) are refused, and FFmpeg gets every output as an absolute `file:` path, so a name starting with `-` is never read as an option. `moments` matches pointing words ("here", "there", "this", "these", "that", "those", "see", "look at", "right here", "over here"), skipping "that" as a conjunction and "there is", and adds the cursor and the clicks within 1 s of each moment.
- Only `record`, `transcribe`, `discard-take` and `setup --install` hold the data folder's process lock (`.instance.lock`), which the desktop app holds while it runs. Everything else, `rename` included, runs beside the app. Every write to a session (app or CLI) takes that session's lock in `<root>/locks/<id>.lock` and re-reads `session.json` before changing it; the lock files live outside the session folders so deleting a recording never races its own lock. The app refreshes the sidebar when its window regains focus, which picks up a CLI rename.
- Output is JSON on stdout and errors on stderr with a nonzero exit. New fields are only ever added (`takes`, `cursor`, `width`/`height`), so existing consumers keep working.

## Persistence and process ownership

Each session groups its metadata, final video, transcript, takes and evidence exports. Persist state transitions so a restart can identify interrupted recording or processing work. Write metadata atomically. Validate identifiers and resolve paths under the configured data directory. The agent interface should report errors on stderr and machine-readable results on stdout.

The sidebar presents optional collapsible sections and ungrouped Recents in one list, without project tabs or a recording-header category picker. Sections reuse the existing project metadata and IDs. New recordings have `projectId: null`; dragging into a section or using Move to section changes only that field, leaving the session directory unchanged. Dropping back into Recents clears it. Section expansion is remembered locally, and unknown section IDs fall back to Recents so recordings remain reachable. The title bar search filters sessions by name only. WebView native file-drop interception is disabled to support HTML drag-and-drop on Windows. Unnamed recordings carry `autoTitle: true` and receive a short title from the first nonempty transcript phrase. An explicit rename, in the app or with `cue rename`, clears that flag. Legacy sessions default to manual titles and retain their existing project IDs, requiring no destructive migration.

Section order is saved atomically in section-order.json. Deleting a section first clears each member recording's projectId, then removes the section metadata. Deleting a recording validates the physical UUID directory under the configured sessions root, rejects linked/reparse paths, and removes its payload before session.json so a locked-file failure remains retryable. UI confirmation identifies the recording and the selected video is unloaded before deleting its files. Runtime ownership guards serialize these operations against capture/transcription start; partial section failures refresh sidebar membership.

Markers left the UI in v0.2.0. The store functions, the `get_markers`/`add_marker` commands and `markers.json` remain for one release so legacy data stays readable; they are deprecated, and the CLI has no marker commands.

Launch dependencies with argument arrays rather than shell-generated command strings. Retain process handles, capture diagnostic output, stop recorders gracefully, and check exit status and output validity before declaring success. Killing an encoder may leave an unfinished container; intermediate recordings and logs should be retained for recovery.

## Dependency setup

Development requires Node.js, the Rust MSVC toolchain, Visual Studio C++ build tools, a Windows SDK, and WebView2. Runtime media work needs FFmpeg/ffprobe and whisper.cpp plus a model. Device capture additionally needs scrcpy and ADB. Pin dependency versions and document their source and license when bundling. Install or download tools into an application-controlled directory; a developer's PATH must not be the only working configuration in a packaged build.

Tools are found in this order: the downloaded runtime in `<root>/tools/whisper-b5454`, `<root>/tools`, the runtime bundled next to the app (`tools/whisper-b5454` in the resource folder or beside the executable), PATH, and on macOS/Linux the standard Homebrew and system binary folders.

The bundled speech runtime is built twice on Windows and Linux x64 (`scripts/build-speech-runtime.mjs`): a plain build that needs only SSE4.2 (the script turns ggml's BMI2 default off), and a build for AVX2, FMA, F16C and BMI2 in the folder's `avx2` subfolder. Wherever `whisper-cli` or `whisper-vad-speech-segments` is found, `deps::tool` runs the `avx2` build beside it when the processor has all four; the plain build is about eight times slower. A final transcription uses half the logical threads, at most 8 and at least 4 where there are that many; a live update uses a quarter, at most 4 and at least 2 where there are that many, beside the capture and its encoder.

Setup checks should distinguish missing executables, missing models, unavailable microphone/output endpoints, and unauthorized/disconnected devices. Only capabilities affected by a missing optional device dependency should be unavailable.
